# Releasing

Releases are cut from `main`. `CHANGELOG.md` holds the notes for the current
release only and is generated by [git-cliff](https://git-cliff.org) from
conventional commit messages, so keep commit subjects in the
`type(scope): summary` form. Notes for earlier releases live in their tagged
commits and on the Releases page.

## Steps

1. Prepare the release. Go to **Actions** → **Prepare release** → **Run
   workflow**, enter the new version (for example `0.7.0`) and run it.

   The workflow bumps the version in `Cargo.toml` and `Cargo.lock`, replaces
   `CHANGELOG.md` with the git-cliff notes for 0.7.0, and opens a
   `release/0.7.0` pull request labelled `release`.

   The same workflow can be dispatched from a terminal with the GitHub CLI:

   ```sh
   gh workflow run prepare-release.yml -f version=0.7.0
   ```

   or, equivalently, `just prepare-release 0.7.0`.

2. Review and merge the release PR.

3. On the [Releases](../../releases) page, draft a new release. Enter the same
   version as the tag, target `main`, click **Generate release notes** and
   publish.

   Publishing pushes the tag. The tagged commit already contains the version
   bump and changelog, and the `Release` workflow builds and publishes the
   multi-arch Docker images to GHCR and Quay.

## Notes

- `CHANGELOG.md` is generated, not edited. Grouping and formatting live in
  `cliff.toml`. To preview the next release locally:

  ```sh
  git-cliff --tag 0.7.0 --unreleased
  ```

- The release notes on the GitHub Releases page are still GitHub's own
  PR-based summary and may differ from `CHANGELOG.md`.
- Release PRs are excluded from generated notes via `.github/release.yml`.
- PRs opened with the default `GITHUB_TOKEN` do not trigger the `Build`
  workflow. Add a `RELEASE_TOKEN` repository secret (a personal access token
  with `repo` scope) to get CI on release PRs.
